# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

AGENTS.md (imported above) holds the layout, commands and invariants. What follows is only what it does not cover. Plan and phase notes live in the Obsidian vault under `Plans/code-automata/`.

## Running a single test

```bash
cargo test --test git worktree_lifecycle                          # one Rust integration test
cargo clippy --target x86_64-pc-windows-msvc --all-targets -- -D warnings   # Windows lint from macOS (core and server; the app needs a Windows C toolchain, CI lints it there)
cd ui && yarn vitest run src/lib/themes/__tests__/theme-config.test.ts   # one UI test file
cd ui && yarn vitest run -t "name of the test"                            # by test name
```

## Rust core

`crates/core` (`ca_core`) holds the task store, phase table and git layer.

- One directory per task: `.code-automata/tasks/<id>/task.json` plus that task's logs. `tests/fixtures/task-example.json` shows every field.
- Each piece of state lives in one place: `phase` is the column, `run` says whether an agent is working, paused, interrupted or failed and on which subtask, a subtask is only `pending`, `done` or `skipped`. Do not add derived or duplicated fields.
- Task files are strict: unknown keys and any `schema` other than 3 are refused, except the older ones, converted on read and rewritten as 3 on the task's next update: schema 1 (3.0) by `store::upgrade_v1` (keys moved under the repository `"."`), then schema 2 (3.1) by `upgrade_v2` (its one `agent` becomes every phase's). `tests/fixtures/task-example-v1.json` is a 3.0 file, `task-example-v2.json` a 3.1 one.
- Each phase has its own agent (`agents: PhaseAgents { planning, dev, qa }`, `PhaseAgents::for_kind`): planning covers questions, plan and subtasks; dev covers triage. A run records its CLI (`run.provider`), and a session is resumed only by that CLI.
- Per-repository state is a map keyed by repository (`"."` for a repository project, the folder name in a workspace): `baseCommits` (its keys are the task's repositories), each subtask's `checkpoints` (only repositories whose HEAD moved), `review.checks`, `pullRequests`. A dev run records each repository's HEAD at its start (`run.heads`); a resume or a dropped run undoes commits after it and never further (an earlier plan's checkpoints stay on the branch after a replan).
- `Task::validate` ties `run` to the phase (plan/subtask_gen → planning, dev → in_progress, qa/checks → ai_review) and a dev/qa run to a pending subtask of its kind. `transitions::apply_move` drops a run the move leaves behind. Branch, worktree paths and each repository's last checkpoint are derived (from the id and HEAD), not stored.
- `TaskStore::update` is the only write path: per-task lock, then atomic temp-file-and-rename. Reads never write.
- Phase moves go through `transitions::check_move`; UI edits through `apply_patch`, which accepts only `EDITABLE_FIELDS`.
- A project (`project.rs`) is a git repository root, or a workspace: a folder in no repository whose every non-hidden direct subfolder is a repository root (checked on every open; the refusal names the others). A folder inside a repository that is not its root is refused, as is anything under `.code-automata/worktrees/`. A workspace task gets a worktree of every repository at start (`worktrees/<id>/<repo>`, rolled back if one fails); its agents run in `worktrees/<id>/`, which is in no repository, so git run under `.code-automata/worktrees/` gets `GIT_CEILING_DIRECTORIES` and never walks up, and files an agent leaves at that folder's top are removed after each run (noted in the run log and the handoff). A folder holding worktrees is never deleted as a leftover. The same repository may also be open on its own; its Worktrees page lists only its own `.code-automata/worktrees/`.

`crates/core/src/agent/` runs agent CLIs (Claude Code, Codex, Gemini CLI, Cursor, Amp, and the scripted `mock-agent` binary for tests):

- A run's outcome comes only from the provider's final `result` event; exit codes are ignored. No `result` means crashed, timed out or stopped, unless the parser's `finish` reads one from the stream's error lines or the last 50 stderr lines (Cursor reports a usage limit only there).
- Usage limits (`agent/limits.rs`): a run that ended because the CLI's subscription limit was reached is `OutcomeKind::RateLimited { resets_at }`. Only the final result, error events and stderr are read, never the agent's own text. The result itself must say it is a limit (its text, or an API 429); a `rate_limit_event` refused earlier in the run (and not allowed again since) only supplies the reset time and the scope, which win over the text's ("resets 3:45pm (Zone)", parsed with `jiff`, first sentence only, up to ten minutes past counts as just passed, more than eight days ahead as a misreading). Codex: "try again at …"; Gemini, Cursor and Amp give no reset time. Amp's error text is in the result's `error` field. Each limit has a scope (`LimitScope`): the CLI's account (session, weekly, Codex, Cursor), one model (Claude's Opus or Sonnet limits; Gemini's quotas, per model), or only the run (a plain 429, Amp).
- Agents and check commands run as their own process tree (`src/proc.rs`). On Unix that is a process group: stop and timeouts send SIGTERM, then SIGKILL after `kill_grace`. On Windows it is a Job Object with kill-on-close: stop kills at once, and the agents die with the engine process. Windows needs no orphan cleanup.
- Finding a CLI (`agent/env.rs`, `Binaries::find`): the file the user chose (`ChosenPaths`, saved per machine in the app data folder's `cli-paths.json`, set through `PUT /api/cli-paths/:provider`), then the provider's install folder (`install_locations`, before `PATH`: an old npm copy under nvm can shadow `claude install`'s native one; only names the installer writes, so `cursor-agent`, not `agent`), then the login shell's `PATH`, then the folders of other node versions (`node_version_dirs`: nvm's `~/.nvm` or `NVM_DIR`, fnm's, nvm-windows'; newest first, `BinarySource::NodeVersion`), then older installs (`legacy_locations`, `~/.claude/local`, after `PATH` so a current copy wins). A chosen file that stops working is an error, not a fallback; preflight's `chosen` lets the UI offer "Find it automatically". `from_env`/`from_search_path` search `PATH` only, so tests never see the machine's real CLIs. Preflight reports which one it used (`source`). A node script found in another version's folder runs on that version's node (`Binaries::launch`: `<version>/bin/node <script>`, for runs and preflight), while the agent's `PATH`, and so every tool it runs, keeps the active node (not on Windows, where npm installs `.cmd` shims).
- Prompts go on stdin, never in arguments. The user's own hooks, plugins, extensions and MCP servers never reach Claude Code, Codex or Gemini CLI agents; logins are shared. Claude: project settings only (`--setting-sources project`, `--strict-mcp-config`). Codex: `--ignore-user-config`. Gemini: `-e none` and `--allowed-mcp-server-names`. Each removes its API-key variables (subscription logins) unless the task sets `useApiKeyFromEnv`. Cursor and Amp load their own configuration as before.
- MCP allowlist (`agent/mcp.rs`): `Settings::mcp_servers` (stdio or HTTP, by plain name; workspace level in a workspace) are the only servers a dev or QA run gets; planning (read-only) gets none, since a server could change things outside the worktree that no discard undoes (QA runs keep them to check the work, and can reach outside the same way). `validate_servers` refuses variables that would change how the agent runs (`PATH`, `HOME`, API keys, `CODE_AUTOMATA_*`) and one variable with two values. Translated per CLI: Claude `--mcp-config <file>`, Codex `-c mcp_servers.<name>={…}` with secrets forwarded by variable name (`env_vars`, `env_http_headers`) and set in its environment, Gemini a settings file named by `GEMINI_CLI_SYSTEM_SETTINGS_PATH`. Secrets never go in arguments; Codex's commands do see a stdio server's variables (it has no file for them). A run's files (`CommandSpec::files`: MCP configs, Codex's schema) sit beside its log in `tasks/<id>/runs/`, are always created new and owner-only (0600 on Unix; on Windows the folder's permissions), removed when the run ends or fails to start (`RunFiles`, on drop), and swept by `Engine::open_with` when a crash left them. `GET /api/mcp/import` lists servers from `~/.claude.json`, the project's (and each workspace repository's) `.mcp.json`, `~/.codex/config.toml` and `~/.gemini/settings.json`; nothing is taken over without a save.
- Codex (`agent/codex.rs`, contract read from its source): `codex exec --json --skip-git-repo-check --ignore-user-config -c approval_policy="never" -C <cwd> --sandbox … [-m] [-c model_reasoning_effort] [--output-schema <file>] [resume <id>] -`. Planning gets the read-only OS sandbox; dev and QA `danger-full-access` (workspace-write cannot reach a linked worktree's git folder or package caches). The schema is made strict (`strict_schema`: every property required, optional ones nullable except arrays). `thread.started` gives the session; `turn.completed`/`turn.failed` is the result, the last agent message the answer; `error` lines are not final.
- Gemini CLI (`agent/gemini.rs`), offered as "Gemini (experimental)": Google ended its free Google sign-in for individuals (November 2026), so it works with an API key, Vertex AI or a company plan, and has had no live run. `gemini -o stream-json --skip-trust -e none --session-id <uuid> | --resume <uuid> [-m] --approval-mode default|yolo` (default refuses tools headless, so planning cannot write; plan mode is not used: it switches itself to yolo). No schema flag: JSON in the final text, as for Cursor and Amp. Not signed in exits 41 with no result; `finish` reads it from stderr. Preflight reads the sign-in chosen in `~/.gemini/settings.json`. `GEMINI.md` is one of the instruction files the prompts name.
- Model lists (`agent/models.rs`, `GET /api/providers/:provider/models`, cached ten minutes): Cursor's `models` and Gemini's `--list-models -o json`, Codex's cached list in `CODEX_HOME`; Claude Code and Amp, or a failed listing, get the app's curated list (`source: curated`).
- Live tests make real model calls: `cargo test --test live_agents -- --ignored --test-threads=1`. Amp spends credit; keep it to `--mode low`.

`crates/core/src/engine/` is the run engine (`Engine`):

- `step::next_step(task, settings)` is a pure function that decides the next step from the task file alone. Change behaviour there and in its table tests, not in the driver.
- `driver.rs` executes one step at a time. Each step's result, and clearing its run, go in one `TaskStore::update`. A run record exists only while a step is in progress or halted (`paused` / `interrupted` / `failed` / `rate_limited`).
- Project memory (`engine/memory.rs`): `.code-automata/memory.md` at the project root. Dev and QA answers may carry `learnings`; after the step's result is written (outside the task lock, serialised by `Inner::memory_lock`) each new one is appended as `- YYYY-MM-DD · <task-id>: <text>` (exact duplicates skipped, 500 characters at most). Every prompt gets the newest lines up to 8 KB through `PromptContext::memory` (in the shared task header, so custom templates get it too). `Settings::use_project_memory` turns both off. A failed write is logged, never a failed step.
- Rate limits (`engine/limits.rs`): `RateLimits` (a CLI, or a CLI's model family (`model_family`), → reset time; a run-only limit is not recorded) is shared by every open project's engine (`Engine::open_with`, `EngineOptions`; the server makes one per process). A run that hits a limit becomes `rate_limited` with `resets_at` (and `reset_estimated` when the CLI gave no time: retried after `unknown_reset_wait`, 30 minutes). A step about to run a limited CLI becomes `rate_limited` without starting anything (checked before the run is written and again after the agent slot is taken). Each such task gets a wake-up (`Inner::schedule_wakeup`: a timer holding a weak engine reference, ticking against the wall clock) that resumes it at `resets_at` plus a grace, only if its run is still waiting for that time. Its run keeps the scope (`limit_scope`). Pause makes it `paused` (also when the driver was just leaving); Resume ("Resume now") forgets the limit first, only while the phase still uses that CLI; its agents may be edited, and moving it to a CLI or model that is not limited resumes it at once. `Engine::open_with` relearns limits and schedules wake-ups from the task files, so a rate-limited task resumes after a restart once its project is open (the one exception to "nothing restarts on its own"); a project not opened yet waits until it is.
- `Engine::open` takes `.code-automata/engine.lock` with `File::try_lock` (one window per project; the holder is named in `engine.owner`, since Windows locks block reads) and reconciles: runs left by another process become `interrupted`, and on Unix their orphaned agents are killed if pid and start time match. Nothing restarts on its own; the user resumes.
- Review (QA) and read-only (planning) runs have their changes, and any commits made during the run, discarded afterwards whatever the provider. Checks run against the last dev checkpoint and fail clearly if HEAD is elsewhere.
- Pull requests (`engine/pr.rs`) give a `PrReport`, one row per repository (pushed, no remote, no changes, failed): a workspace task goes through every changed repository, keeps each success at once and goes on past a failure; descriptions list the other PRs (GitHub kept complete with `gh pr edit`, GitLab as known at its push). A one-repository task's failure is the call's error. Each repository's host (`PrHost`): the `pullRequestHost` setting (`repos.<name>.pullRequestHost` in a workspace), else detected from `origin` (an SSH alias is resolved with `ssh -G`; github.com, or a name part starting "gitlab"; a host `gh auth token --hostname` has a login for is GitHub Enterprise; else `other`, with a note to the user). GitHub: `gh`; only a link recorded for GitHub is edited as a PR. GitLab: push options on every push (GitLab opens or updates the merge request), its link read from the push's `remote:` lines (`link_from_push`: an opened request, else a create page, nothing else); no link at all is an error, not a record. Other: plain push; a weaker link never replaces a kept one (`better_link`). Push options cannot hold newlines, so the GitLab description is one line. The UI never calls a pushed branch a pull request. Tests whose remote is a local folder set the host explicitly.
- Acceptance tests run the whole engine on the mock agent (`tests/engine.rs`); the crash test drives the `ca-engine` binary in a child process and SIGKILLs it. One live run through Claude: `cargo test --test live_engine -- --ignored --nocapture`.

`crates/server` (`ca_server`) is the HTTP API (axum) the UI talks to; the desktop app runs it in-process:

- `127.0.0.1` only. Every request needs `Authorization: Bearer <launch token>` and a `Host` of `127.0.0.1:<port>` or `localhost:<port>` (DNS-rebinding guard). CORS only for `Config::allowed_origins` (the app's own page; empty for `ca-server`): a preflight from one of those is answered without the token, every other request still needs it.
- The project comes from the percent-encoded `X-Project-Path` header. One `Engine` per project root (repository or workspace), opened on first use and kept until the server stops, so other projects' tasks keep running.
- Handlers are thin: each calls one `Engine` method (`create_and_start` exists for that reason). `CoreError` maps to a status in `src/error.rs` (`Invalid` means the command does not fit the task's state, so 409).
- `GET /api/events` is Server-Sent Events: `hello` first (load the task list then), then `task` (the full task, or none when deleted), `agent`, `error` and `lagged` (resync).
- Each agent run also writes `<run>.events.ndjson` (`engine/runlog.rs`): a start line, then normalized `AgentEvent`s, which `GET /api/tasks/:id/runs/:name` replays.
- The UI's types in `ui/src/lib/api/types/` are generated by ts-rs from the Rust types (`#[cfg_attr(feature = "ts", ...)]`). After changing a serialized type: `rm -rf ui/src/lib/api/types && cargo test -p code-automata-core -p code-automata-server --features ts export_bindings`. CI fails if they differ. Map `i64`/`u64` fields to `number` with `ts(as = "f64")`.
- `tests/http.rs` drives the real router with `oneshot` on the mock agent. It finds core's `mock-agent` binary in the target directory, so build the workspace first when running `-p code-automata-server` alone.

## Desktop app (`crates/app`)

- `main.rs`: `Server::start` (`server.rs`) binds `127.0.0.1:0` before the window exists, then resolves the login-shell `PATH` and serves; early requests wait in the backlog. The window's initialization script sets `window.__CODE_AUTOMATA__ = {baseUrl, token}`. The page is `tauri://localhost` (`http://tauri.localhost` on Windows), a stable origin, so localStorage survives restarts; the server allows exactly those origins (plus Vite's in debug builds).
- Quit (window close, Cmd-Q) goes through `request_quit`: a confirm if tasks run, then `Server::stop`, which stops every engine (runs left `interrupted`), then exit.
- The page may call only the commands listed in `build.rs` and allowed in `capabilities/main.json`; a new command goes in both, in `generate_handler!`, and in `ui/src/lib/native.ts`. Paths from the page must pass `paths::inside_open_project` (an existing folder inside a project the server has open).
- Navigation stays on the app's pages; `http(s)` links open in the default browser.
- `CODE_AUTOMATA_SMOKE=1` (`smoke.rs`) checks the webview → server → webview path on a scratch repository, prints `smoke: passed` and exits; `app.yml` runs it on all three OSes. Debug builds offer the mock agent when `CODE_AUTOMATA_MOCK_AGENT` (and optionally `CODE_AUTOMATA_MOCK_SCENARIO`) is set; release builds never do.
- Updates (`update.rs`): release builds check `latest.json` of the newest GitHub release 5 s after launch and ask; installing stops the server like a quit, then restarts. "Newest" is GitHub's latest, which skips pre-releases, so pre-releases never update to each other. A version that failed to install is recorded (`update-failed` in the app data folder) and not offered again. The public key is in `tauri.conf.json`; the private key is the `TAURI_SIGNING_PRIVATE_KEY` secret (kept outside the repo). Losing it means installed apps can no longer verify updates.
- Open in terminal (`terminals.rs`, commands `available_terminals`/`open_in_terminal`): a terminal at a worktree (or a workspace task's folder), the one chosen in the app settings (`terminal`) if installed, else the first found. macOS: Terminal, iTerm, Warp with `open -a`; Ghostty, WezTerm, kitty as a new instance given the folder. Windows: `wt -d`, else PowerShell with `CREATE_NEW_CONSOLE` (overriding `proc::command`'s hidden console). Linux: the terminal's working-directory flag, else `x-terminal-emulator` started in the folder.
- App settings (`app_settings.rs`): `app-settings.json` in the app data folder (`checkUpdatesAtLaunch`, `terminal`), read through the `get_app_settings`/`set_app_settings` commands; an unreadable file is moved aside. `check_for_updates` is Settings' manual check: one check at a time (`CHECKING`), and unlike the launch check it offers a version recorded in `update-failed`. The app tells the page what the updater is doing (`UpdateEvent` through the channel the page passes to `watch_updates`, kept in `store/update-store.ts`): Settings shows "Checking for updates…", and after "Install and restart" `components/update-progress.tsx` shows the download (a bouncing bar until 1%, then the percentage), then "Installing". The updater's HTTP client has a connect timeout (shared among a host's addresses: one GitHub download address that never answers otherwise costs the OS TCP timeout, about 75 s on macOS) and a read timeout. Only failures worth it are retried (`retryable`: connect, timeout, broken transfer, 5xx/429): a check once, a download twice, all within one 15-minute deadline. On macOS the restart after an install is `RELAUNCH_SCRIPT`, a detached `sh` that waits (at most 30 s) for this process to exit, then `open`s the bundle and checks that it runs, falling back to `open -n` (Tauri's restart runs `open -n` while the old process lives, which leaves a second Dock icon); it logs the outcome to `relaunch.log` in the log folder.
- Log file: `tauri-plugin-log` in the OS log folder (`~/Library/Logs/com.code-automata.desktop/code-automata.log` on macOS): start, port, the resolved `PATH`, engine errors, quit.

## UI (`ui/`)

- `store/project-sync.ts` follows `GET /api/events` for the open project (`lib/api/events.ts`, fetch-based SSE that reconnects on its own). `hello` and `lagged` reload the task list; `task` messages upsert or remove; `agent` messages fan out through `lib/agent-events.ts` to the run log viewer.
- Workspace tasks in the UI: `review-summary.ts` reads every per-repository map (`taskRepos`, `changedRepos`, `reposToCheck`); Human Review shows the single PR card for a repository project and `repoPrViews` rows for a workspace, both driven by `POST /api/tasks/:id/pull-requests` (`PrReport`). The Worktrees page groups a task's worktrees (`groupWorktrees`); a card's chips are `repoChips`. `project-store` keeps each opened folder's kind (`projectInfo`).
- Commands go through `act()` in `store/task-store.ts`: it stores the task the server returns and toasts a refusal (the server's 409 message is written for the user).
- `lib/task-view.ts` maps a task to its status, badge and single primary action. A card shows that action; anything else is in the details view. A rate-limited run is its own status ("Rate-limited", "Resumes at …" or "Retrying at …", action "Resume now"); the details list each phase's agent (`agentLines`).
- The task dialogs pick agents per phase (`lib/agent-form.ts`: `PhaseDrafts`, `defaultDrafts`; `components/tasks/agent-picker.tsx`: `PhaseAgentPicker`, `ModelField`): one agent for all phases (the radio list, as before) or a CLI, model and mode per phase. The default is the last choice (localStorage `code-automata-last-agents`) while its CLIs are offered, else the first ready CLI, with Fable 5.2 / Opus 5.5 / Fable 5.2 for Claude Code. Models come from `GET /api/providers/:provider/models`, plus "Default" and "Other…". The same-agent box appears only once the agents have loaded.
- Settings: "MCP servers for agents" (form rows `McpRow`, saved with the settings; Import from `GET /api/mcp/import`), "Project memory" (its own editor and save, `GET/PUT /api/memory`; the on/off switch is in the form), and, in the app, the terminal choice beside the update settings (one component, so the file is written from one copy).
- Task dialogs are opened through `store/task-view-store.ts` and rendered once by the board (`kanban/task-dialogs.tsx`), not inside the card: a card is recreated when its task changes column, which would close a dialog it held.
- Dragging only moves (`POST /api/tasks/:id/move`); nothing starts an agent but a button.
- Worktrees page: an orphan (no task file) is deleted with its branch; a done task's worktree can be removed on its own (`Engine::delete_worktree`: folder only, task and branch stay); reopening the task (Done → Human Review) brings it back from the branch (`Worktrees::restore`). Any other task's worktree goes with the task.
- To try the UI by hand: run `ca-server --allow-mock --mock-scenario <file>` on a scratch repository and `yarn dev`; a mock task created in the dialog plays that scenario (see `crates/core/src/bin/mock_agent.rs` for the step format).

## End-to-end (`ui/e2e/`)

- `harness.mjs` starts `vite preview` once and a fresh `ca-server --allow-mock --mock-scenario <file>` per scenario on port 7878, each with a new repository; `rules(devs, extra)` builds the mock scenario (put `extra` rules first to fail, hang or slow one step; `once()` plays a rule only the first time).
- Drive the page through `data-testid`s and DOM clicks (`click`, `cardAction`): agent-browser's pointer clicks can land on a card that is moving between columns. Never trigger a browser dialog (`confirm`, `alert`); confirmations are inline.
- A failed scenario leaves a screenshot in `ui/e2e/artifacts/` (CI uploads it).
- `e2e/demo.mjs` (`yarn demo`) records the README's video and screenshots the same way, headless at 1920×1080, into `ui/e2e/artifacts/demo/`. Its project is a small repository at `/Users/Shared/code-automata-demo/code-automata` (removed afterwards) whose tasks are 3.2's features; mock rules match a task's title and step (`whenPrompt` as a list). `ca-server --demo-as claude` (with `--allow-mock`; `Binaries::with_stand_in`) offers the production agent list without Mock and has the mock play Claude Code's tasks, which preflight reports as ready. `docs/images/ca.png` is its `board.png` set into the tablet frame of the original image (screen area 166,145 to 1369,812).
- Git runs with `GIT_OPTIONAL_LOCKS=0` and retries a write that hit a held `index.lock`: the e2e suite found the UI's worktree status reads colliding with the engine's resets.
